# Backend audit and modernization roadmap — 2026-11-06

## Scope and confidence

Static review of FastAPI routes, Firebase access, Firestore rules, AI services, quota and scraping controls, tests, container and GitHub workflows in this checkout. No credentials, live cloud resources, customer data, or external providers were accessed. Findings labeled **verified** describe observable code; exploitability in a deployment depends on deployed revision, rules, network and IAM. **Hypothesis** means an operational concern requiring production evidence. Severity assumes an internet-accessible service with authenticated users. Effort is a rough engineering estimate, not a commitment, and excludes rollout/approval lead time.

## Immediate decisions

**Do not expand paid traffic until ownership, entitlement and quota enforcement are fixed and verified.** Resume and interview data are sensitive; unchecked access is the most consequential product risk. Determine whether the repository Firestore rules are deployed before claiming direct-client exploitation. Restrict costly endpoints or apply a temporary hard service-level cap while durable fixes are released. Do not assume budget alerts enforce a spending ceiling.

## Findings

### P0 — Cross-user interview access and mutation (verified)

`backend-microservice/app/server.py:1423` and `:1478` accept an authenticated user but fetch a globally keyed session without comparing its `user_id` to the caller; `app/database/firebase_db.py:520` likewise reads by ID alone. `server.py:1367` processes a globally keyed in-memory interview without checking the stored `user_id`. Anyone who obtains another session ID can read the stored interview or submit answers to its active session. Random UUIDs reduce discoverability, not authorization. Admin SDK calls bypass client Firestore rules.

**Fix:** make repository reads and mutations require owner ID and return indistinguishable 404s; enforce ownership before processing, including report routes; review every ID-bearing endpoint. **Acceptance:** two-user tests cover each route for own, other, absent and malformed IDs; no provider call or write on denial. Estimate 1–2 engineer-days plus review.

### P0 — Client-writable entitlements and unmetered system-funded AI (verified code; deployment conditional for rules)

`firestore.rules:15` allows an authenticated owner to write all fields of their `user_settings` document. `app/services/usage_service.py:100` trusts `plan=pro` as unlimited and `:155` exempts anyone with a nonempty `user_api_key`. If these rules are deployed and direct client access is available, the owner can set plan, counters or reset date. Independently of direct Firestore access, `server.py:211` and `:1251` expose `user_api_key` setting; resume analysis (`:542`) uses the system OpenAI key and live interview (`:1531`) uses the system Gemini key while `_enforce_quota` exempts any user with any key. Thus a user can submit an arbitrary nonempty key and avoid limits on system-funded routes. `/analyze/resume` (`:1490`) uses Gemini without any quota check. The rules do not establish whether these paths are enabled in production.

**Fix:** move billing entitlements and usage to backend-only collections, deny direct writes, validate billing events, and exempt only calls actually executed using a validated user-supplied credential. Gate all system-funded endpoints and apply global concurrency, cost and account ceilings. Treat billing limits and rate limiting separately. **Acceptance:** emulator tests reject direct tampering; a dummy BYOK key cannot bypass any system-funded call; all billable routes are inventoried and metered; provider failures and month rollover are covered. Estimate 3–5 days plus billing integration.

### P1 — Unsafe upload filenames and uncontrolled memory (verified)

Live preparation constructs file paths with `os.path.join(tmp, resume.filename)` and `job_description.filename` (`server.py:1548`). Client-controlled absolute paths or `../` components can escape the temporary directory; actual write scope is limited by the app process permissions. `_validate_upload` (`:288`) reads the entire upload before testing its size, allowing oversized bodies to consume memory before rejection. PDF extraction is synchronous and accepts untrusted documents.

**Fix:** generate server-owned filenames, constrain ingress body size before multipart parsing, stream with a hard limit, and sandbox/cap extraction by pages, time and output size. **Acceptance:** absolute/traversal filenames remain inside temp directory, oversized chunked bodies are rejected early, malicious and malformed PDFs cannot stall the service. Estimate 2–4 days.

### P1 — Outbound request and SSRF boundaries (verified design gap; exploitation untested)

`app/services/job_link_parser.py:54–106` validates DNS before `httpx` separately resolves the hostname, leaving a DNS rebinding/time-of-check gap; `client.get` buffers the response before inspecting Content-Length, so the stated response limit is not a streaming limit. Relative redirect handling is manual. Separately `SettingsUpdateRequest.base_url` is arbitrary (`server.py:222`) and flows to the OpenAI client (`server.py:1286`, `app/services/interview_system.py:63`), creating another user-controlled outbound destination. Exact impact depends on network policy and client behavior; no network exploit was attempted.

**Fix:** prefer explicit provider endpoint allowlists; isolate scraping behind egress filtering and bind DNS validation to the actual connection, validate every redirect and stream with a byte ceiling. **Acceptance:** integration tests using controlled DNS, redirects, IPv4/IPv6, private/link-local destinations, missing/false lengths and oversized streams; infrastructure denies metadata/private network access. Estimate 3–6 days.

### P1 — Quota races and failure-open accounting (verified)

`server.py:583–616` checks a snapshot, resets and increments separately; `firebase_db.py:334–364` acknowledges read-then-write overshoot and returns false on errors, which caller ignores. Concurrent requests can exceed limits and concurrent window resets can overwrite counts; Firestore errors can allow calls with no recorded usage. `/interview/start` charges before file validation (`server.py:1302–1308`); `/profile/resume` creates a processing document before quota check (`:645–655`), leaving an orphan if denied.

**Fix:** transactional reservation with period, entitlement, idempotency key and bounded concurrency; explicitly settle/release failed work under a documented product policy. Return an actionable transient error when the spend-control store is unavailable. **Acceptance:** concurrent tests prove no overspend at the limit and no lost increments on rollover; rejected work leaves no processing record; retries do not double charge. Estimate 3–5 days.

### P1 — Volatile sessions, background jobs and partial persistence (verified)

Both `_active_sessions` and `_live_sessions` are process dictionaries (`server.py:282`); restarts and traffic across instances lose interviews. BackgroundTasks are in-process (`:41–85`, `:619–655`) and a sweeper marks stalled jobs failed rather than resuming. `deploy.yml:51–52` fixes one Cloud Run instance; this does not protect against revision replacement, crashes, or maintenance. Resume completion is written before parsed sections, usage and profile (`server.py:550–563`) and write return values are ignored, so a completed status can coexist with missing results. Live session creation also ignores its return (`:1660` onward). `firebase_db.py:371–400` filters `session_data` to `safe_data`, dropping supplied `report_data` and `interview_type` (`server.py:1660–1675`).

**Fix:** persist session state and versioned transitions; use durable queue/worker with bounded retries, leases and idempotent writes; store results before publishing completion, and record failure states. Persist a typed report contract and check every persistence outcome. **Acceptance:** kill worker mid-task, retry delivery, restart and change instance; completed jobs have complete consistent data, and no duplicate billable operation or record. Estimate 2–3 engineer-weeks including migration.

### P1 — Sensitive data and credential lifecycle (verified storage; operational policy unverified)

User provider keys are stored in ordinary Firestore settings (`firebase_db.py:279–330`); `GET /settings` masks the API response (`server.py:1239`) but repository rules allow owners to read the whole document. Resume text, parsed sections, interview conversations and reports are persisted (`firebase_db.py:891`, `:371`). Gemini uploads have a deletion method (`gemini_file_service.py:38`) but the live route does not call it (`server.py:1518–1692`). Provider retention, deployed IAM, backups, actual deletion behavior, and contractual obligations were not verified.

**Fix:** keep credentials in a dedicated restricted encrypted secret store; provide key rotation/removal, retention and account deletion across primary records, backups and provider files; delete uploaded provider files in finally/reconciliation and avoid PII in logs. Document processors, regions, retention and consent. **Acceptance:** deletion inventory and automated integration tests cover associated data and provider cleanup, with audit trail and a defined backup expiry. Estimate 1–2 weeks, plus legal/product decisions.

### P2 — Availability and operational observability (verified / hypothesis)

Firestore SDK calls are synchronous in many `async` routes and background functions (`server.py:538–563`, `:1423`); slow calls can block the event loop. `/health` always reports process health (`:362`); `/admin/health` performs a database probe, is unauthenticated and always returns HTTP 200 (`:367`), so HTTP-only monitors cannot identify database failure. `firebase_db.py` often catches exceptions and returns `None`, empty data or false, and list endpoints return empty lists on failure (`server.py:1409–1464`), masking outages as empty state. **Hypothesis:** blocking and one instance can produce tail latency or outage under load; measure before sizing.

**Fix:** move blocking work off the event loop or use an async client, propagate typed errors, define liveness/readiness separately, add request/trace IDs, metrics for dependencies, jobs and cost, SLO alerts and runbooks. Protect or simplify detailed probes. **Acceptance:** dependency failure returns predictable 5xx while liveness stays responsive; load test records p95/p99, error rate and event-loop lag; dashboards and alerts tested. Estimate 1–2 weeks.

### P2 — AI quality, cost and reliability (verified design; model quality unmeasured)

Resume analysis performs parsing, up to seven concurrent section calls and holistic review (`resume_analyzer_service.py:98–140`), with timeouts, retries, text caps and token recording. Responses request JSON but are parsed with `json.loads` without a complete typed semantic contract (`:187–207`, `:267–287`); prompts incorporate untrusted resume/JD text. The system has no demonstrated evaluation set, calibrated scoring, prompt versioning, input-instruction isolation, per-call pricing ledger or end-to-end generation budgets. This is a gap in repository evidence, not proof of low output quality. `server.py:334–359` silently returns `{}` on missing key or model failure, masking degradation.

**Fix:** version prompts and schemas; validate outputs with typed bounds and bounded repair; separate user content from instructions, test injection and unsupported claims; capture actual input/output tokens, provider/model and cost per operation without recording sensitive content. Establish offline consented, representative goldens and blind quality review. **Acceptance:** evals measure groundedness, consistency, schema validity, injection resistance, latency and cost; failure is explicit; budget thresholds gate model/prompt releases. Estimate 2–4 weeks for initial evaluation and instrumentation.

### P2 — Rate limits and deployment supply chain (verified)

`server.py:117–131` keys limits by raw bearer token prior to identity verification and uses the default limiter storage; rotating tokens changes buckets and instance-local state does not coordinate replicas. Some expensive routes or WebSockets do not share a common global cost limiter. `deploy.yml` deploys on main independently of the CI workflow, uses a long-lived service-account JSON key and broad roles, and has no deployment smoke test or rollback step. Dependencies include unbounded lower-only versions (`requirements.txt`, e.g. `google-genai`, `firebase-admin`, LangChain integrations); container uses a mutable base tag. Existing Docker process does run as non-root.

**Fix:** verified-UID and IP limits backed by shared storage, connection/stream limits and provider spending ceilings; gate deployment on CI, use short-lived federated identity and least privilege, pinned reproducible dependencies/base digest, vulnerability scanning, staged release and rollback. **Acceptance:** token rotation and multi-instance tests cannot evade limits; deploy blocks on failed checks and rollback is rehearsed. Estimate 1–2 weeks.

## Tests and verification

The repository has focused tests for authorization, quotas, SSRF, stale sweeps, analyzer failure and endpoints (`backend-microservice/tests/`); CI runs most backend tests with coverage, explicitly excluding `test_api_pytest.py` (`.github/workflows/ci.yml:27–38`). Presence does not establish the missing cross-tenant and distributed invariants. An attempted local CI-equivalent test run could not start: `../.venv/bin/pytest` returned permission denied. No tests or cloud resources were modified. Run in the supported Python 3.12 environment, then add Firestore emulator rules/transaction tests, two-user route tests, adversarial file/network tests, provider contract tests and restart/fault-injection tests. Avoid real provider calls in ordinary CI; run separately budgeted integration tests.

These ranges overlap only with sufficient parallel staffing; dependencies determine critical path. Estimates are engineering person-time and exclude vendor approvals and compliance certification. Prioritize a reliable, useful interview/report loop before feature expansion. Instrument the funnel from upload to completed analysis to repeat interview, segment failed work and paid conversion, and validate users' willingness to pay before assuming unlimited Pro is viable. Model contribution margin as price collected minus payment fees, provider tokens/files, infrastructure and support, using observed traffic and retry rates; no production volumes or price data were provided, so no revenue or ROI forecast is defensible yet.
