# Beta signup operations

`POST /beta-signups` accepts JSON with `email`, `consent: true`, and optional `website` honeypot. The API lowercases and trims the email, validates it, and uses its SHA-256 digest as the Firestore document ID. A first signup atomically creates a document in `beta_signups` with `email` (normalized string), `consent` (boolean true), and `created_at` (Firestore server timestamp). A repeat returns the same success response without changing the original record. A filled honeypot also returns success but is not saved. Storage failures return 503. The rate limit is five requests per minute per IP per backend process; it is not a distributed abuse or spend control.

Before launch, deploy the backend to a project with Firestore enabled and grant its runtime service account the minimum Firestore permissions needed to create documents. Confirm that the deployed Firestore rules deny client access to `beta_signups`; the repository's default deny rule covers this collection. Confirm production ingress passes a trustworthy client IP to the application, and use an edge or shared-store rate limit if multiple instances or proxy behavior make the in-process limit insufficient. Test a signup, repeat, storage failure and direct client denial in a non-production project. Restrict operator access: the collection contains personal information, and a hash of an email is not anonymous.

There is no automatic invite delivery, email verification, export, opt-out handling, or deletion workflow in this implementation. Assign an authorized operator and approved process for reviewing signups, sending invitations, handling deletion requests and suppressing contacts who withdraw consent. Define and publish the exact retention period and deletion schedule before collecting production signups; no automatic expiration is configured. Align signup consent copy and privacy notice with the intended contact and retention practices. Monitor storage errors and rate limits without logging email addresses.
